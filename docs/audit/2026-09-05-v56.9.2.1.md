The runtime publishes two channels out of one stream. Every daily build is a
prerelease, and the release that `/releases/latest` serves moves only when a
vetted daily is promoted — a one-way step, since flipping a release back to
prerelease leaves that URL serving it anyway. The three install commands on the
site are built against `/releases/latest/download`, so the binary a reader gets
by copying the install line is the stable one and nothing else. That is why the
pages pin stable rather than the newest tag: a shortcoming fixed only in a daily
is not yet fixed for the person following the instructions on the page, and a
page that retired the flag would be lying to them. This run therefore re-verified
every claim at `v56.9.2.1` and used `v56.9.5.1` only for the path-to-green lines,
which say what has already landed and is waiting to be promoted. Thirty-four
footnotes across the five pages carry the daily tag; every other footnote
resolves against stable.

## Per level

Counts before the run are read from `git show bf5bde3:docs/matrix/<file>`;
counts after are read from the working tree. "Flags" are the callout lines the
pages carry — verified claim, shortcoming, path to green, and the three
argument verdicts. They are classified against the text they had before:

- **confirmed** — the claim still holds and the line is unchanged, or gained
  only citations;
- **extended** — the verdict is unchanged and the line gained new facts (most
  often a path-to-green sentence naming a daily-channel fix);
- **flipped** — the claim itself changed: a colour change, a claim moved to the
  past tense or narrowed, or a path-to-green statement that had been overtaken;
- **added** — a flag that did not exist before.

Confirmed + extended + flipped equals the count before; plus added, the count
after.

The pin mechanism changed during this run: before it one repository-wide
constant fixed every level to the same release, and now each level carries its
own tag, so a page whose owner accepts only small deltas is not dragged forward
by a re-verification of the others. The value is the same on both sides —
`v56.9.2.1` — because stable did not move.

## Method

Two checkouts on real disk, one per tag, sharing an object store so the two can
be diffed: the stable release every level pins and the newest daily. Nothing was
copied into the site repository and neither checkout was written to.

Each slice of the work — one per explanation level, one per advertised
capability, one per security layer, plus one for the release diff and one for
the page specifications — was given to an auditing agent that had to name a file
and a line range for every claim, and then to a skeptic whose job was to refute
those claims against the same checkouts. Where a skeptic refuted an entry or
listed one the audit missed, the skeptic's finding overrode the audit. Several
of the corrections in this record come from that pass rather than the first
one: the two sibling scripts that still create the enclave network without the
isolation flag and are invisible to the new gate; that the control-wire readers
are not in fact single-sourced, so the daily's fix there is partial; and the
withdrawal of the commit-count figure. The first pass caught the others — that
the global-configuration and uninstaller shortcomings were already stale at the
pinned release, and not only in the daily. The pages were then written, reviewed
and corrected the same way: a writer per level working from the verified audit, a
reviewer checking the result against the code again, and a corrector applying
what the review found.

The gate is the checked build. It resolves every footnote target against the
checkout for the tag that footnote names — the level's pin, or the daily for a
path-to-green line that acknowledges an unpromoted fix — and searches for the
quoted text inside the cited line range after collapsing whitespace, failing if
the file is missing, the range falls outside it, or the quote is not there. No
claim in this record or on the pages rests on an agent's assertion alone; every
quote was matched against the bytes at the tag it names. The run for this record
reports 22, 29, 141, 93 and 44 footnotes for levels one to five, all resolving,
317 of the 329 carrying a verbatim quote — the twelve without one are the
external references on level five.

## What could not be verified here

- **How many commits separate the two tags.** Both checkouts are shallow: the
  stable tree reaches one commit and counting the revisions between the tags
  across the shared object store returns 1. The "900 commits" figure that
  appears in the runtime's own release ledger is that ledger's text, not a
  measurement this run could reproduce, and it is repeated as fact nowhere on
  the pages. What the object store does support is the size of the diff: 799
  files changed, 59,941 insertions, 3,300 deletions.
- **Anything requiring a macOS or Windows host.** No such host was reachable
  from this session. Every claim about the virtual-machine boundary, the
  keychain, Credential Manager, notarization and the Windows installer rests on
  the repository's own code, specifications and recorded measurements, and is
  stated that way. The macOS model-cache survival claim in particular is
  recorded as unproven for exactly this reason.
- **The published site.** `https://tillandsias.org/` is not reachable from this
  forge — the connection is reset, the project's own domain having reached the
  proxy allowlist only in the daily channel — so the pages were verified as
  source and as a local build, not as served HTML.
- **The size of the run itself.** The agent counts this run reports — fifty-four
  in the audit phase, twelve in the first writing phase, seven in the second,
  six for this record and its issue drafts, and twelve in the final verification
  — are the run's own bookkeeping from the launcher's output. Nothing in the
  repository or in either checkout records them, so unlike every other figure
  here they cannot be reproduced from the artifacts.
- **Fleet-versus-repository questions.** The repository can say what a release
  contains; it cannot say what is installed. Whether the two machines found
  carrying a world-readable key have since been repaired, whether every host has
  installed the release that carries the fix, and whether an enclave network
  created before the isolation fix still exists on some machine are all outside
  what a checkout can answer. Where a page asserts something about the fleet it
  cites a recorded measurement and says so.

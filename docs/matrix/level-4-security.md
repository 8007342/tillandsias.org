# Tillandsias, explained like you are an IT / security expert

## WHAT IT IS

Tillandsias is a locally-hosted, ephemeral compute enclave for running coding agents against your source. The pitch is containment: you give an LLM agent a shell, and everything it can touch is deliberately bounded. Free software, no telemetry, no vendor backend — `PRIVACY.md` states there is no server operated by the project that your install talks to, and there is no analytics or crash reporting SDK to contradict it.

**Layering.** On Linux there is **no VM**: `tillandsias-headless` runs on the host and drives rootless Podman directly — README states Podman is the only host dependency there, and `crates/tillandsias-vm-layer` carries per-OS transports (`wsl.rs`, `vz.rs`, `transport_windows.rs`) with its Linux `fake` module gated behind a test feature. On Windows the tray provisions a WSL2 Fedora distro; on macOS a Virtualization.framework Fedora guest (no krunkit/libkrun — not evidenced). So the hypervisor boundary you may be assuming exists on Linux **does not**. Host↔guest control is vsock/HvSocket.

**Isolation envelope.** `crates/tillandsias-podman/src/policy.rs` defines `MANDATORY_HARDENING_FLAGS` — `--userns=keep-id`, `--cap-drop=ALL`, `--security-opt=no-new-privileges`, `--security-opt=label=disable` — and `validate_launch_argv()` rejects `--privileged`, a non-`keep-id` userns, `--cap-add=ALL`. The only allowlisted passthrough is `--device=<path>` (GPU). Containers run as uid 1000. Note the fourth flag honestly: **SELinux labelling is disabled on every container**; MCS labelling for the forge domain is `planned` in `openspec/specs/default-image/spec.md`, not shipped. Seccomp customization: not evidenced.

**Network.** `podman network create tillandsias-enclave --internal` — no default route, aardvark-dns resolves container names only. Only the proxy is dual-homed (`ENCLAVE_EGRESS_NETS`). Squid on `:3128` is **default-deny** against `images/proxy/allowlist.txt` (207 lines), denials issued as `TCP_RESET`. There is **no iptables/nftables anywhere** — enforcement is network placement plus `HTTP_PROXY` env injection.

**The TLS interception question, answered precisely.** Yes there is ssl-bump and a trusted CA, but interception is exact-host and narrow: `ssl_bump peek` at step 1, `bump` only for SNI `release-assets.githubusercontent.com`, `splice all` otherwise. GitHub APIs, package registries, and every auth endpoint stay end-to-end. Upstream verification is retained — `tls_outgoing_options cafile=/etc/ssl/certs/ca-certificates.crt`, with an in-config standing order never to add `DONT_VERIFY_PEER`. The CA is a self-signed RSA-2048, 30-day cert generated by `ensure_ca_bundle` into `/tmp/tillandsias-ca` (`openssl req -nodes`, `rsa:2048`) — per-install, **not** per-launch, and `openspec/specs/proxy-container/spec.md`'s claim of an EC P-256 per-launch root+intermediate chain on tmpfs does not match the code. The private key reaches Squid only as a Podman secret at `mode=0400`; the entrypoint `exit 1`s if it is absent. It got there the hard way: `755-qcxh` found that key **0644 in `/tmp`** — any local uid could mint certs the enclave trusts — and `772-shi9` found macOS preambles re-widening it. The same CA also signs the nix binary-cache leaf, so it is not solely a MITM key.

**Secrets.** HashiCorp Vault in a container, enclave-only, file storage on `tillandsias-vault-data`, TLS leaf from the enclave CA, no host port (except a loopback compat mapping on native Linux). Forge containers get **no broad Vault token** and, by default, no host project bind mount at all — the workspace is a `git clone` from a per-project enclave mirror. The GitHub OAuth token never enters the forge: the `tillandsias-git-<project>` mirror holds AppRole material (`/run/secrets/vault-approle`, 48h SecretID, client tokens re-minted at their 24h max TTL, sunk to tmpfs only) and relays pushes upstream via a credential helper on stdin, never argv — a fix for a real `/proc/<pid>/cmdline` leak.

**Blast radius, stated bluntly by the repo.** `podman-idiomatic-patterns/spec.md` says a container escape lands as **the invoking user's UID on the host**, with `$HOME`. `docs/cheatsheets/enclave-architecture.md` adds: host compromise is total compromise, and the allowlist is generous by design — DNS- or header-encoded exfil to an allowed domain is possible. The allowlist admits `.amazonaws.com`, `.googleapis.com`, `.cloudflare.com`, `.netlify.app` — anyone-can-publish namespaces. Since only one host is bumped, there is **no payload inspection**: the proxy sees SNI/CONNECT hostnames.

**Known bypasses, all self-documented.** Image builds egress directly with `--dns 8.8.8.8` ("outside the trust boundary"). `run_provider_login` is dual-homed and, measured on two hosts, reaches `pypi.org` and `example.com` — "the attachment does not grant 'GitHub push', it grants the internet." The project browser sets no `--network` at all. Env vars are trivially unset by an agent; only the `--internal` netns actually stops it. The `git://` receive-pack mirror listener is anonymous: "network placement SHALL NOT be described as client authentication."

## HOW IT WAS BUILT

The governing method is *Monotonic Reduction of Uncertainty under Verifiable Constraints* (`methodology/philosophy.yaml`). Two invariants matter to a security reader: `verification_claims_must_be_falsifiable`, and `evidence_is_not_proof`. Green is a signal, not a guarantee, and the repo says so.

**Spec-to-code binding.** Every active spec must carry a `@trace spec:<name>` annotation, at least one executable litmus test per MUST, and cheatsheet provenance; `ambiguity.score` must be 0. `scripts/validate-traces.sh` refuses ghost traces and orphan specs. Verification is laddered: **S0–S3** for spec maturity (S2 = every MUST litmus-bound; S3 = gates PRs and emits runtime trace linkage) and **L0–L3** for code annotations, where a declared level is a *claim* CI re-derives and downgrades on mismatch. The reason `security-privacy-isolation` reads as a real contract rather than a slogan is that its four "zero-tolerance" boundaries each terminate in a named litmus.

**Supply chain — what is genuinely verifiable.** Release artifacts are signed with **Sigstore cosign keyless**: no long-lived key, identity is the GitHub Actions OIDC token, inclusion proof in Rekor, one `.cosign.bundle` per asset plus signed `SHA256SUMS*`. `scripts/check-release-asset-integrity.sh` enforces transitive coverage. Workflow actions are SHA-pinned (one exception: `cache-nix-action@v7`, tag-pinned). The Linux musl lane is nix/crane with `flake.lock` rev-pinned nixpkgs.

**What is not verifiable, said plainly.** The verification identity regexp is `https://github.com/.*/tillandsias/` — it does not pin the org, workflow, or ref. There is **no SBOM**, no `cosign attest`, no SLSA/in-toto predicate, no container-image signing, and no reproducible-build claim. Container base images are pinned by **tag, never by digest** (`fedora-minimal:44`, `alpine:3.22`, `hashicorp/vault:1.18`, `caddy:2-alpine`) — mutable-tag provenance. macOS builds are **ad-hoc signed and unnotarized**, and the installer clears `com.apple.quarantine`. Windows `.exe`/`.zip` ship unsigned when no Trusted Signing account is configured; unsigned MSIX is now *withheld* on the honest reasoning that an absent asset beats an inert one. And the advertised `curl … | bash` one-liner verifies nothing — `install.sh` is signed, but the pipe does not check it.

**Ephemerality as a control, and its limits.** Forges run `--rm`; `/tmp`, `/run/user/1000`, `/opt/cheatsheets` are tmpfs; the browser profile dies with the window; uncommitted in-forge work is destroyed (hence AGENTS.md's "a finding you did not push is a finding you destroyed"). What **persists**: the per-project git mirror volume (the only durable copy of committed work), the tool cache volume, `vault-data` and its audit device on a host dir, the shared read-only nix store, and — critically — the Vault Shamir share in the **host OS keychain**. Ephemerality therefore resets compute, not identity. `900-z3kv` proved this: on Linux, `podman system reset --force` is *not* credential-cold — three hosts asserted an empty store, then a "pristine" init logged `recovered Shamir unseal share from host keychain` and `preserving existing data volume`, meaning the vault re-init path the smoke claims to exercise has never run on Linux. Windows had the mirror-image failure (`803-49re`): a stale share bricked GitHub login, and the packet was deliberately **left open** because Part A only helps hosts that wipe after the fix.

**Agent autonomy and auditability.** Agents execute only inside forges (`forge-as-only-runtime`); no host-side agent binary is permitted. Two channels deliberately cross back out and are the surfaces to review first: the tray control socket (`0600`, postcard framing, 64 KiB cap) bind-mounted RW into every forge, and `host-browser-mcp`, which lets a contained agent drive a **host** Chromium via `browser.eval`/`click`/`type`. The host↔guest exec path is authenticated (`Noise_NNpsk0_25519_ChaChaPoly_BLAKE2s`, PSK = HKDF-SHA256 over the running binary's own SHA-256, separated per hop and per build version) and allowlisted (`exec_allowlist.rs`) — but note what that authenticates: possession of the same released binary, not the identity of the tray. `release_root_secret()` falls back to a hardcoded `DEV_ROOT_SEED` under `debug_assertions`, and its own docstring defers per-boot mixing of a host-controlled secret to an open packet (order 142) — but read `plan/issues/security-audit-zero-trust-2026-07-01.md` for how it started: `VMADDR_CID_ANY`, a self-reported `Hello`, and verbatim argv exec. The audit trail — `plan/index.yaml`, `plan/issues/`, `plan/mo-full-attestations.d/` — is committed and unusually candid, but it is agent-self-reported and **unsigned**; no commit signing is evidenced. `940-f77j` (a red tree stamped green) is fixed to be "unforgeable by accident, **not by intent**." Take that as the honest summary of the whole audit posture.

# Level 3 — Power User

## WHAT IT IS

Tillandsias is a small, private cloud region that lives on your machine and disappears when you stop it. You install one binary; it brings up a Fedora guest, and inside it a rootless Podman stack: `tillandsias-vault`, a bare git mirror service, `tillandsias-proxy` (Squid, forward), `tillandsias-router` (Caddy, reverse), and a per-project **forge** container that your coding agents run in. They share an internal Podman network created with `podman network create tillandsias-enclave --internal`, so nothing on it can reach the internet directly. Only the proxy is dual-homed onto an egress network. That's the whole trick: an isolated region with exactly one door.

Getting one running is a curl and a click. On Linux, `curl -fsSL .../install.sh | bash`, and Podman is the only host dependency. On Windows you run `tillandsias-tray.exe` and it provisions a Fedora WSL2 distro; on Apple Silicon `install-macos.sh` provisions a Fedora VM under Virtualization.framework. Then you point it at a project directory and attach. From a terminal that's `tillandsias --headless /path/to/project` plus `--claude`, `--codex`, `--opencode`, or `--bash`; from the tray it's the same `podman run` with a host terminal wrapped around it. `--init` builds and starts the stack, `--reset-guest` throws it all away and reprovisions, and `--publish-local` exposes a project web container.

The rule that shapes everything is `forge-as-only-runtime`: `claude`, `codex`, `opencode`, and `bash` exist **only inside the forge image**, never on your host `$PATH`, and the tray refuses to launch an agent if the image is missing rather than falling back to a host binary. Mounts into the forge are exhaustively enumerated — your project directory at `/home/forge/src/<project>`, a read-only enclave CA cert dir, `tmpfs`, and a per-launch `mktemp -d`. Your `$HOME`, `~/.config`, `~/.cache`, and host keychain are unreachable from inside — there is even a regression test named `launch_forge_agent_does_not_mount_user_home`.

**Ephemeral** is the load-bearing word. Uncommitted work inside a forge is gone when the container stops — `AGENTS.md` puts it in capitals: a finding you did not push is a finding you destroyed. In the default mode the forge doesn't work on your directory at all — it does `git clone git://git-service/<project>` from the enclave git daemon, and `remote.origin.pushurl` is rewritten so every agent push transits the mirror's pre-receive relay on its way upstream. (A host-mounted mode exists via `TILLANDSIAS_PROJECT_HOST_MOUNT=1`.) **Idempotent** is the companion: every layer is built to come up clean from scratch, so the declared response to a broken container, guest, or stack is destroy-and-recreate, never hand-patch — error messages are required to say so, with the exact command.

What survives stopping the stack (and what does not):

- The bare mirror in the volume `tillandsias-mirror-<project>`, plus your host working copy, which the tray fast-forwards from the mirror on every push — non-destructively, skipping any dirty tree, detached HEAD, or non-fast-forward.
- Vault secrets in the `tillandsias-vault-data` volume, unsealed from a Shamir share held in your host's native keychain, never a passphrase prompt.
- The Ollama model cache, which is a host bind mount at `~/.cache/tillandsias/models` rather than a volume — so even `podman system reset` leaves it alone.
- Not `--reset-guest`, though: it deletes every `tillandsias-`-prefixed container, volume, and secret — mirrors and vault included — and rebuilds from scratch. Push first. `scripts/uninstall.sh` is gentler, keeping the VM image and cache unless you pass `--wipe`.

Everything else — the forge container, the router, the proxy, the network itself — is rebuilt on the next attach. Web services never publish ports: `tillandsias-router` binds `127.0.0.1:<port>` only (80, falling back to 8080) and routes `<service>.<project>.localhost` to internal ports from a generated `dynamic.Caddyfile` — `opencode` to 4096, `vite` to 5173, `next` to 3000, `jupyter` to 8888. Nothing listens on `0.0.0.0`.

## HOW IT WAS BUILT

The method has a name and it is the project's core principle: **monotonic reduction of uncertainty under verifiable constraints**. Read it as a loop, not a slogan. Specs declare intent; litmus tests turn each requirement into an observable signal; code implements; traces prove the code ran; CI refuses anything that breaks the chain. Every edit is supposed to reduce uncertainty about one named boundary, and the convergence engine in `methodology/convergence.yaml` states the objective as minimizing four gaps at once: spec↔code, code↔cheatsheet, cheatsheet↔reality, and litmus-binding↔spec.

Specs live in `openspec/specs/` — 177 of them, one directory per capability (`forge-as-only-runtime`, `enclave-network`, `git-mirror-service`, `tillandsias-vault`, `subdomain-routing-via-reverse-proxy`), each written as MUST/SHOULD requirements with numbered `#### Scenario:` blocks. Specs carry a verification level: **S0** draft, **S1** syntactically valid with an ambiguity score of zero, **S2** litmus-bound (every MUST has at least one executable signal), **S3** runtime-validated with traces emitting spec linkage. Code annotations carry a parallel **L0–L3** ladder, and CI validates the declared level against the observed one — claiming L3 without a passing litmus is itself a failure. Litmus tests are 411 YAML files under `openspec/litmus-tests/`, wired to specs by `openspec/litmus-bindings.yaml`, which records a coverage ratio per spec and tombstones the obsolete ones. `scripts/` holds 437 shell scripts including 96 `check-*.sh` guards and 181 `test-*.sh` — and `./build.sh --check` before every push is the only trunk protection, because push CI was deliberately deleted to stop burning the Actions budget — `.github/workflows/` holds exactly one file, `release.yml`, and it is `workflow_dispatch` only.

Progress is measured, not asserted. **CentiColons** (`methodology/proximity.yaml`) are a bounded ranking function over a finite obligation lattice: each spec gets a denominator from weighted obligations — 100 for a MUST, 120 for an invariant, 100 for a negative litmus signal — and obligations earn credit only when the evidence is queryable and the linked artifact exists at the cited revision. "2778/2800 cc" means 22 CentiColons of named, inspectable work remain. The loop then picks the *worst* residual to attack next rather than the easiest passing test — and it measures closure, not confidence: the methodology is explicit that evidence is not proof, that CentiColons are not probabilities, and that it is not claiming a metric contraction.

The coordination layer is where the CRDT mechanics show. Work is filed as **packets** in a plan ledger. `plan/index.yaml` is a compacted base and a declared concurrency block — nobody edits it in place. Instead each host writes new immutable fragments to `plan/index.d/`, named `<utc>-<suffix>-<host>.yaml`. Reading the ledger is `base ⊕ fold(fragments)` in filename order, which is chronological because the name is UTC-first. Two properties make it conflict-free: one writer per file (a host writes a path only it could have produced, so git never conflicts) and immutability after writing (so the fold is order-independent and idempotent). Per field: packets are a **G-set** keyed by `packet_id`, events are a **G-set**, status is an **LWW-register** resolved by `(ts, host)` — deliberately not applying LWW to lists, because that would discard the loser's entries. Compaction is text-level and never re-serializes YAML, after a `serde_yaml` round-trip was found to drop the ledger's inline operator rulings.

- Versions are epoch-anchored CalVer — `<years_since_epoch>.<month>.<day>.<build>`, so `56.9.2.1` is 2026-09-02 — from a single `VERSION` file, never the wall clock, so rebuilding an old tag reproduces its version.
- Releases ship as prereleases; `scripts/promote-stable.sh <tag>` flips one to stable and *requires* curl-install e2e PASS evidence in `plan/` naming that exact tag.
- Convergence is asymptotic across versions, not terminal within one: the enforceable rule is that measured debt must be non-increasing at each release boundary, and the project declines to claim it reaches zero.
